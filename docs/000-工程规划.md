## 1. 背景与定位

### 1.1 一句话定位

**以 AAR 形式发布的、Android 版 `node` 命令行可执行**——一份交叉编译的 `libnode_cli.so`
（arm64-v8a，exec 型 PIE），在终端里由 node-pty 经 `forkpty` + `execve` 启动，为 PTY 提供
`node` 命令；assets 随包 npm/corepack JS 树（纯数据，不需要 exec 位）。

### 1.2 为什么需要它

- 原生 Android 没有现成的 node：`/system/bin` 只有 mksh 与 toybox；
- 进程内引擎（`libnode.so`）每进程只能 `node::Start` 一次，且不是可 `exec` 的文件形态；
  终端（PTY）天然多进程，需要**独立进程的 node CLI**；
- `node::Start` 每进程一次的约束对 CLI 不构成障碍——CLI 是独立进程，与进程内引擎互不冲突。

### 1.3 边界

| 在范围内 | 不在范围内 |
|---|---|
| `libnode_cli.so` 的交叉编译、exec 型 ELF 门禁、AAR 打包、发布 | 任何嵌入 API / Kotlin 桥（属 aosp-node-bridge） |
| npm / corepack JS 树的随包与 sha256 出处记录 | pty 会话管理 / 终端 UI（属消费方或 aosp-node-shell） |
| 版本配对事实源 `node-cli.lock.json` | node 引擎共享库（`libnode.so` 由 aosp-node-runtime 提供） |

## 2. 与 `aosp-node-runtime` 的配对关系

1. **版本恒等于 Node 版本**：`io.github.fellow99:node-cli:<node>` ↔ `node-runtime:<node>` ↔
   `node-pty:<node>`，三者在消费方 APK 内必须同版本（与 pty 同一纪律）。
2. 配对是**版本纪律**而非编译期链接：CLI 与引擎是两个不同形态的制品
   （exec 可执行 vs dlopen 共享库），互不 `DT_NEEDED`。
3. runtime 升版是本仓的强制重编事件（跟随机制在 M4 建立）。

## 3. 技术方案

### 3.1 制品形态

```
node-cli-<ver>.aar
├── jni/arm64-v8a/libnode_cli.so   # exec 型 PIE（ET_DYN + PT_INTERP=/system/bin/linker64，16KB 对齐）
└── assets/node-bridge-tools/…     # npm/corepack JS 树（纯数据）
```

- 产物**只有这一个 `.so`**；`libc++_shared.so` 由 node-runtime 统一供给（绝不随包，防同名冲突）；
  exec 时须 `LD_LIBRARY_PATH=<nativeLibraryDir>`。
- 打包：**`useLegacyPackaging=true`**（extractNativeLibs=true）——targetSdk≥29 的 SELinux
  禁止从可写数据目录 exec，nativeLibraryDir 是唯一合规执行位；库不落盘则 `execve` ENOENT。
- 命名为 `libnode_cli.so` 而非 `libnode.so`：引擎 soname 已被 node-runtime 占用，同目录不可重名。

### 3.2 exec 型门禁 profile（与 dlopen 库门禁的差异）

| 门禁 | 判据 | 与 pty 门禁的差异 |
|---|---|---|
| ELF 形态 | `ET_DYN`（PIE） | 同 |
| 解释器 | **PT_INTERP 恰 1 个且 = `/system/bin/linker64`** | **相反**（pty 要求 PT_INTERP=0） |
| 依赖 | **DT_NEEDED 白名单**（系统库 + lock 登记） | pty 是"必须含 libnode.so" |
| NAPI | 无门禁 | pty 有"napi_* 未定义引用"门禁 |
| 页对齐 | 16KB | 同 |
| 出处 | sha256 / size / 源版本 / NDK / flags | 同 |

### 3.3 构建链路（M1 实现；000-scaffold 固化接口）

1. `fetch-node-cli-source.mjs`：官方 `node-v<ver>.tar.xz`，校验 SHA-256，不改源；
2. `build-node-cli-android.sh`：`android-configure` **不带 `--shared`** + `--with-intl=none`
   + `-Wl,-z,max-page-size=16384` → `make` → `llvm-strip --strip-unneeded` → 输出 `libnode_cli.so`；
3. `provision.mjs --out`：exec 门禁 → 投放 jniLibs + assets → 写 META-INF 元数据。

开放问题（M1 拍板）：NDK 版本线（与 runtime 对齐）；npm/corepack 树的精确物化目录与
marker 纪律；pnpm JS 树是否随包钉版。

## 4. 唯一事实源：`node-cli.lock.json`

镜像 `pty.lock.json` 纪律：版本 + 大小 + sha256 + 配对 runtime + 门禁 + 出处，二进制不入库。
当前唯一 release 记录为 **draft**（size=0、sha256 为空、status=draft）——按 FR 纪律：
draft 不伪造哈希，首个真实 CI 构建后回写事实。

### 5.1 发布模式（GitHub Release 先行、Maven Central 随后）

沿用 aosp-node-pty 的两段式发布：

1. **先行：GitHub Release（M1，tag `v26.13.0` 推送触发真实流水线）**——产出
   `node-cli-v<ver>-android-arm64-v8a.tar.gz`（libnode_cli.so + npm/corepack 树 +
   BUILD/FETCH-METADATA + LICENSES）与 `.sha256`，lock 回写 `status=released`（GitHub 事实）；
2. **随后：Maven Central（M3）**——执行口径按工作区
   [`docs/发布到maven-central.md`](../../docs/发布到maven-central.md) runbook：
   §2 一次性凭据（Central Portal Token + GPG，仅用户级 `~/.gradle/gradle.properties`）→
   §4 发布前检查（二进制就位 / 版本三处对齐 / `publishToMavenLocal` 结构断言）→
   §5 上传（`gradle :node-cli:publishToMavenCentral -PRELEASE=true` → Portal 点 Publish）→
   §6 核验 + 回填 `mavenCentral.published=true`。

- 本仓 `publish.gradle.kts` 已内置该管线（vanniktech 0.37.0、RELEASE=false 默认、
  POM SCM url 补丁指向本仓）；
- 与 pty 的差异：版本源为 `CLI_VERSION`（恒等于配对 Node 版本）；配对纪律同 pty——
  runtime/pty/cli 三件必须同版本上线（runbook §10 已登记本线复用）。

## 6. 质量门禁汇总

| 门禁 | 判据 | 在哪强制 |
|---|---|---|
| ELF 形态 | ET_DYN（PIE）、PT_INTERP=系统 linker64、AArch64、16KB 对齐 | provision + CI |
| 依赖白名单 | DT_NEEDED ⊆ 系统库 + lock 登记库 | provision（本工程特有） |
| 不入库 | jniLibs/**/*.so 与 assets 树被忽略 | .gitignore + review |
| 可复现 | 干净 runner 上单条 workflow 可重出同口径产物 | CI（M1） |
| 许可 | Node MIT + npm Artistic-2.0 + corepack MIT | THIRD-PARTY-NOTICES.md |
| 发布卫生 | RELEASE=false 默认；Token/GPG 不入库 | gradle.properties / publish |
