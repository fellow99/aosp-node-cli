## 1. 系统用途与目标用户

### 1.1 一句话

本系统是一个**以 AAR 形式发布的、Android 版 `node` 命令行**：与 `aosp-node-runtime` 同一棵官方 Node.js 源码树交叉编译出的 exec 型可执行（arm64-v8a），在终端里由 node-pty 经 `forkpty` + `execve` 启动；npm/corepack 的 JS 树作为纯数据随包分发。本系统**不含任何嵌入 API、不含 JS 运行时封装**——只有该二进制及其随包树的可复现构建、门禁校验与发布流水线。

### 1.2 目标用户

| 用户 | 他们要什么 | 本系统给什么 |
|---|---|---|
| **消费方应用开发者**（主用户） | 在自己的 App 里提供一个真 `node` 命令（终端/PTY 场景），不维护交叉编译 | 一个版本化 AAR（exec 型二进制 + 随包 JS 树）+ 配对纪律 |
| **消费方构建流水线作者** | 一条命令把「校验过、形态正确」的制品接进 APK，重复执行无副作用 | 事实源文件 + 校验/投放工具 + 退出码契约 |
| **本仓维护者 / 评审者** | 判定一项产物是否合格、一次变更是否越界 | 可证伪的门禁判据（§4）与证据纪律（宪法 C7） |
| **上架合规责任人** | 证明包内没有不该进的东西（引擎库、C++ 运行时同名库）、第三方许可齐备 | 命名禁区恒拒 + 许可清单交付物 |

### 1.3 非目标（明确不做，规划 §1.3）

1. **不做嵌入 API / Kotlin 桥**（属 aosp-node-bridge 线）。
2. **不做 pty 会话管理 / 终端 UI**（属消费方或 aosp-node-shell）。
3. **不做进程内 Node 引擎**——`libnode.so` 由 aosp-node-runtime 提供；本仓制品与之是**两个形态**（exec 可执行 vs dlopen 共享库），互不依赖挂靠。
4. **不做 pnpm 本体**——pnpm 12+ 为 Rust 可执行件，走独立 `aosp-pnpm-cli` 线（工作区方案 §9.3）。
5. **不做 x86 / x86_64 / arm32**——只发布 AArch64。
6. **M1 前不承诺可用的二进制**——当前一切「产物事实」（体积/ELF 实测值/真机行为）均为 ⬜。

| # | 能力面 | 必须让使用者做到什么 | 现状 |

## 3. 系统边界

### 3.1 在范围内

| 域 | 内容 |
|---|---|
| 构建系统与版本纪律 | AAR 容器工程、版本恒等于配对 Node 版本、三制品同版上线纪律（规划 §2） |
| 交叉编译（M1 ⬜） | 官方源码获取（不改源）、Android 配置（无 `--shared`、`--with-intl=none`）、16KB 页、strip 与唯一命名 |
| 门禁与投放 | exec 型 ELF 门禁七项、依赖白名单、命名禁区、幂等投放、版本元数据 |
| 随包树（M1 ⬜） | npm/corepack JS 树收集/剪枝/manifest（逐文件 sha256）、壳脚本打入与白名单校验（规划 §5/§6） |
| 发布 | GitHub Release 先行 + Maven Central 随后（两段式，规划 §10.1）；许可清单随 Release 归档 |
| 出处与可复现 | 事实源文件的 draft→released 回写纪律；NDK/flags/patch 出处记录（规划 §8） |

### 3.2 不在范围内（归消费方 / 其他制品线）

环境引导层（assets 物化、env 注入、symlink 农场的**产品实现**）· PTY 会话与终端 UI · 嵌入 API/Kotlin 桥 · 进程内引擎（`libnode.so`）· pnpm 本体 · 上架材料 · `npm i -g` 安装脚本的 shebang 改写器（M2 可选评估项 ⬜，规划 §7）。

### 3.3 运行期能力边界（消费方文档必须写明；规划 §7「已知限制」）

| # | 边界 | 性质 |
|---|---|---|
| B1 | **设备无编译器**：安装任何带 node-gyp 原生构建的 npm 包**必失败**；失败必须如实上报（非 0 退出 + 明确的编译器缺失信息），**绝不静默降级** | 能力边界，非缺陷；反例验收见探针 P7 ⬜ M2 |
| B2 | **npm 原生包不可装** ⇒ `npm i` 只承诺**纯 JS 包**可用（如装后可 `require`） | 正例验收见探针 P6 ⬜ M2 |
| B3 | `npm i -g` 装出的 bin 脚本落在应用可写目录（不可 exec），且其 `#!/usr/bin/env node` 在 Android 上不可寻 ⇒ 只能经 `npx` 或 `node <脚本路径>` 显式调用 | 能力边界（规划 §7.1） |
| B4 | corepack **禁止**用于获取 pnpm/yarn 可执行件（运行期下载可执行件被纪律禁止）；corepack 仅 `--version` 与钉版 JS 兜底 | 纪律边界（R6） |
| B5 | Intl API 不可用（`--with-intl=none` 为**有意取舍**，与 runtime 引擎的 small-icu 分歧已登记）；Temporal API ⬜（若 M1 拍板禁用则与 runtime 同口径） | 有意分歧（D7/R10），消费方文档必须写明 |

## 4. 功能需求（RFC 2119：MUST / MUST NOT / SHOULD / MAY）

> 编号沿用 `specs/000-scaffold/spec.md` §3；每条判据必须**可证伪**。现状列：✅ 已实现可验证 / ⬜ 属后续里程碑。

### 4.1 工程骨架（F1）

| 编号 | 级别 | 需求 | 可证伪的验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-001 | MUST | 根工程名固定为 `aosp-node-cli`，且仅包含唯一 Android library 模块 `node-cli` | 配置期任务清单中根工程名与模块集合恰为该两者 | ✅ |
| FR-000-002 | MUST | `node-cli` 模块 MUST 是 Android library：命名空间 `org.fellow99.nodecli`、minSdk 24、compileSdk 36、ABI 仅 arm64-v8a | 模块配置快照四项与该值逐一相等 | ✅ |
| FR-000-003 | MUST | 发布坐标 MUST 是 `io.github.fellow99:node-cli:<CLI_VERSION>`；`<CLI_VERSION>` MUST 恒等于配对 Node 版本；MUST NOT 使用 `NODE_` 前缀的构建属性名 | 未设置版本属性时配置期**报错**（而非静默默认值）；属性名以 `CLI_` 开头 | ✅ |
| FR-000-004 | MUST | 原生库打包 MUST 采用「解包落盘」模式（exec 型硬要求，与 dlopen 库相反） | 打包配置该开关为 true；产物 AAR 的 `.so` 以解包方式分发 | ✅（开关）/ ⬜（产物级验证 M1） |
| FR-000-005 | MUST | 工程 MUST 能在不投放任何二进制的情况下完成配置期与任务求值 | 干净检出（无任何 `.so`）上配置期成功 | ✅（TC-01 实测） |

### 4.2 事实源（F2）

| 编号 | 级别 | 需求 | 可证伪的验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-010 | MUST | 「版本 + 大小 + 摘要 + 配对 runtime + 门禁键 + 出处」MUST 只有**一个**权威出处文件，且纳入版本控制 | 全仓检索不存在第二份同语义清单；校验/投放工具只从该文件读期望值 | ✅ |
| FR-000-011 | MUST | **draft 记录 MUST NOT 伪造哈希**：首个真实 CI 构建前，size/sha256 MUST 为空值占位 | 当前记录 size=0、sha256 为空、状态标 draft；校验工具在 draft 下只记录不比对 | ✅ |
| FR-000-012 | MUST | 门禁键集 MUST 反映 **exec 型 profile**：含「解释器=系统 linker」与「依赖白名单」两键；MUST NOT 含 dlopen 库的「必须含引擎库」「napi 可解析」键 | 键集合与该清单逐一比对 | ✅ |
| FR-000-013 | MUST | 事实源 MUST 记录配对 runtime 的坐标与发布标签 | 记录值 = `node-runtime:26.13.0` / `v26.13.0` | ✅ |

### 4.3 门禁与投放（F3）

| 编号 | 级别 | 需求 | 可证伪的验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-030 | MUST | 校验/投放工具 MUST 实施**七项 exec 门禁**，任一项不过 MUST 以退出码 2 硬失败（无「警告后继续」档位） | 门禁表七行一次给全；任一不过 ⇒ 退出码 2 且不产出投放文件 | ✅ 工具 / ⬜ 真实样本（TC-13） |
| FR-000-031 | MUST | 门禁 MUST 强制 exec 形态：PIE 共享对象类型、**解释器段恰 1 个且指向系统动态链接器**、AArch64 指令集 | 一个无解释器段的 dlopen 库样本 ⇒ 解释器门禁失败、退出码 2 | ✅ 工具 / ⬜ 负样本补测 |
| FR-000-032 | MUST | 依赖门禁 MUST 是**白名单**：动态依赖 ⊆ 系统库 + 事实源登记的随包库；页对齐门禁 MUST 要求 16KB | 白名单外依赖 ⇒ 失败；LOAD 对齐 < 16KB ⇒ 失败（bring-up 放行必须显式且带警告） | ✅ 工具 |
| FR-000-033 | MUST | 出处门禁 MUST 比对摘要与大小；draft 无锁值时 MUST 明示「仅记录不比对」 | draft 下输出含该明示文案且不因此失败 | ✅（TC-06 实测） |
| FR-000-034 | MUST | 投放 MUST 只写入唯一原生件（命名固定 `libnode_cli.so`），并落版本元数据 | 投放后目标目录恰一个新原生件 + 一份元数据文件；重跑不重复写（幂等口径见 plan） | ✅ 工具 / ⬜ 首次投放 |
| FR-000-035 | MUST | 引擎库 `libnode.so` 与 C++ 运行时 `libc++_shared.so` MUST NOT 进入本 AAR（防止与配对 runtime 包内同名冲突） | 投放时若目标目录存在两者之一 ⇒ 报错；校验时兄弟原生件规则判定其它 `.so` 非法 | ✅ 工具 |
| FR-000-036 | MUST | 投放 MUST 写出版本元数据（工具版本 / ABI / 文件名 / 大小 / 摘要 / 配对 runtime / 投放时间） | 元数据文件存在且字段可逐项核对 | ✅ 生成逻辑 / ⬜ 首次投放 |
